# AidBridge: threat model and evidence

Status: development build, synthetic data only. Nothing here has been run against real beneficiary records.

## 1. System and design decisions

Stack: FastAPI, PostgreSQL 18, Jinja2 server-rendered pages. Python 3.14. Noise from diffprivlib 0.6.6 (requires scikit-learn below 1.9; versions are pinned in `requirements.txt`).

Scenario: a cash and services assistance program. Gender-based violence caseloads are the highest-sensitivity extension and are discussed, not implemented, because real caseloads are often too small for useful answers at these noise levels.

| Decision | Choice | Why |
|---|---|---|
| Query scope | A small engine: measure = count or mean of monthly transfer; up to two group-bys from region (8), household size (12) and transfer band (10); optional filters chosen from the same fixed lists; at most 150 cells per query. Column expressions come from a whitelist and values are bind parameters, so no free text reaches SQL. No arbitrary SQL. | Each query shape has a known sensitivity. |
| Mechanism | Laplace with basic composition | One mechanism with matching accounting. |
| Privacy unit | One record per pseudonymous ID per dataset (see limits in section 4) | Count sensitivity 1. |
| Count sensitivity | 1 | Add/remove adjacency. |
| Grouped counts (histograms, cross-tabs) | Every cell is always returned, including empty ones. A person is in exactly one cell, so the cells are disjoint and the whole table costs one count query. | The set of cells present would leak. |
| Mean | Noisy sum divided by noisy count, epsilon split evenly. Sum sensitivity is 500 (values clipped to [0, 500] in SQL). A noisy count of 1 or less is refused. | Noise is never added to the mean directly. |
| Post-processing | Counts floored at 0 and rounded; means clipped to [0, 500] | Free post-processing, but biases small groups. |
| Budget | Global per dataset: total 10.0, per query 0.1 (count, however many cells) and 0.5 (mean). Spend-only, never reset by the app. | Chosen from the evaluation in section 3. |
| Preview | Before charging, the analyst sees cost, cell count, typical error and budget left. These use only public facts (epsilon, noise scale, number of cells), never true group sizes. Preview spends and writes nothing. | The analyst can decide with full information. |
| Suppression | A cell whose noisy count is below 30 is shown as suppressed. It depends only on the noisy value, so it is free post-processing. It is a usability flag, not a privacy protection: an empty cell still shows a value about 2.5% of the time. | Protection comes from the noise and the budget. |
| Stored results | Each run stores its noisy cells in a results table (append-only for the app role) so refresh and CSV download cost nothing. Only the owning analyst can open a result (others get 404). | Noisy outputs are post-processing of an answer already charged. |
| Atomicity | Check and spend in one transaction with a row lock (`SELECT ... FOR UPDATE`) | Concurrent requests cannot both pass the check. |
| Refusals | A refused mean is charged and logged | Refusal depends on the noisy count, so it is not free. |
| Order | Spend first, compute second, release last, one transaction | An answer is never released without a charge. |
| Roles | `field_agent` (write only), `analyst` (aggregate queries only), `admin` (audit log and budget view) | Enforced in the API; the database sees one app role. |
| Pseudonyms | Random 64-bit token generated by the server at intake | The agent never supplies or sees an ID. |
| Audit log | Append-only for the app role (UPDATE, DELETE, TRUNCATE revoked). Logs user, query type, parameters, epsilon, and a SHA-256 hash of the result. | Admin sees who asked what, never results. |
| Sessions | Signed cookie holding only the user id; role re-read from the database on every request; 8 hour expiry; HttpOnly; SameSite=Strict; CSRF token on every POST | Role cannot be forged by editing the cookie. |
| Passwords | argon2; unknown usernames still run a dummy hash check | Equalises response timing. |
| Login limiting | 5 failures per username or 20 per IP in 5 minutes locks login, even for the correct password | Slows online guessing. |
| Matching flow | A requester posts a need, a verifier approves or rejects it, and approved needs appear on a public board and map. A supporter pledges to a published need, the verifier arranges the handover outside the platform, and then marks the need fulfilled or releases it back to the board. No money moves through the platform. | Connects people without handling payments or contact between strangers. |
| Needs data | Needs, pledges and events live in their own tables, apart from the analytics dataset. Each need stores a private description and contact, and the public text is written by the verifier. A CHECK refuses to publish a need without public text. | Only reviewed text can reach the public. |
| Status order | A trigger allows only pending to published or rejected, published to pledged, and pledged back to published or on to fulfilled. A unique index allows one active pledge per need. | A bug in a route cannot skip verification. |
| Pledging | A supporter can hold at most 3 active pledges (counted under an advisory lock), gives a contact detail that only verifiers see, and can cancel until the handover is arranged. The verifier arranges the handover, marks the need fulfilled or releases it with a reason. Each action is a conditional update that applies once and writes an event. | Keeps matching mediated: the two people never see each other's details. |
| Places | Province and district are chosen from fixed lists (81 provinces, 973 districts) and validated as a pair. Names are plain ASCII. | Clean place data for the map, and for analytics later. |
| Public board | No sign-in. Only published needs, showing month, category, province, district and the verifier's text. No cookies, a limit of 60 requests a minute per address, and a map drawn from our own files with no third-party tiles. | Public by design, so it shows as little as possible. |
| Sign-up and roles | Requesters and supporters can sign up. Verifiers, analysts, admins and field agents are created by script. Sign-ups are throttled per address. | Nobody can promote themselves. |

## 2. Threat model

### 2.1 Curious analyst

Goal: learn about individuals from query answers.
- Repeating a query averages the noise away (demonstrated in `attack_sim.py`). The global budget caps the total epsilon spent, so repetition is limited.
- Only three fixed query types exist, with bounded inputs. There is no free-form SQL.
- Small groups give noisy answers. The smallest region (193 people) has about 5% count error and about 5% mean error at the chosen settings.
- Residual risk: the guarantee is epsilon 10 over the dataset's lifetime under basic composition. That is a weak guarantee in absolute terms, chosen for utility, and the write-up does not call it safe.

### 2.2 Colluding analysts

Goal: pool queries across accounts to get more than one analyst could.
- All analysts draw on one global budget per dataset, so extra accounts do not multiply the privacy loss.
- Residual risk: denial of service. One analyst can spend the whole budget and lock everyone else out. Per-user caps were in the original design as optional and are not implemented.
- Tested: `test_collusion.py` runs two analyst accounts against one budget (see section 5). Combining answers across accounts is argued from composition, not tested.

### 2.3 Stolen database

Goal: read data from a copy of the database.
- Passwords are argon2 hashes. The session signing key is in `.env`, not the database, so a database copy alone does not allow forging sessions.
- Beneficiary IDs are random, so they do not link to real identities inside the database.
- Residual risk, and the largest one: beneficiary rows (region, household size, transfer) are stored in plain text. Field-level encryption was cut from scope. Those fields can act as quasi-identifiers. The audit log also reveals which queries analysts ran.

### 2.4 Compromised field agent

Goal: read data back, probe for records, or corrupt the dataset.
- The role is write-only. The submit page returns only "Submitted" and no ID. Tests show an agent gets 403 on all analyst and admin routes.
- Server-generated pseudonyms mean an agent cannot probe which IDs exist.
- Every submission writes an audit row.
- Each agent is capped at 200 submissions per 24 hours (`DP_FIELD_DAILY_CAP`), counted from the audit log, with an advisory lock so concurrent requests cannot exceed it. Over the cap the route returns 429 and saves nothing.
- Residual risk: data poisoning is slowed, not stopped. A patient attacker staying under the cap still shifts the data over weeks, and clipping to [0, 500] bounds one record but not many. The audit log makes the volume visible to the admin.

### 2.5 Admin

Goal: use the admin role to read data or hide activity.
- The admin page shows audit rows (who, what, parameters, epsilon, a 12-character hash prefix) and the budget. It never shows results. Tests show the admin gets 403 on every analyst query route and on field submit.
- Residual risk: the admin sees what analysts asked about. Accounts are created by a seed script that needs database credentials, because there is no account management page.
- The database owner (`postgres`) is outside the app's controls. The owner can read every row, alter the audit log, and reset the budget. Append-only is enforced against the app role only.

### 2.6 Matching side: actors and what each can see

AidBridge has two halves that share one application but not their data. The matching side holds the `needs`, `pledges` and `need_events` tables. The analytics side holds the synthetic beneficiary dataset, its privacy budget and its audit log. No query connects the two yet.

| Actor | Can see | Cannot see |
|---|---|---|
| Anyone, no account | Published needs: the month posted, category, province, district and the verifier's text. The number of published needs per province on the map. | Pending, rejected, pledged and fulfilled needs. Private descriptions, contact details, and who posted a need. |
| Requester | Their own needs: category, place, status, description and any rejection note. | Other requesters' needs. Their own contact detail is not shown back to them. |
| Supporter | The public board, the verifier's text of published needs, and their own pledges with a status. | Private descriptions and contact details, other supporters' pledges, and the requester's identity. |
| Verifier | Every need in full: private description, contact method and detail, place and time. Every active pledge, with the supporter's username and contact. Writes the public text, decides, arranges handovers, marks needs fulfilled and releases pledges. | The analytics data. |
| Analyst | Noisy aggregates of the synthetic dataset. | Individual records, and any needs. |
| Admin | The audit log of the analytics side (who asked what, with parameters and result hashes) and its budget. | Needs, results and contact details, through the application. |
| Field agent | Nothing read back. Adds records to the synthetic dataset. | Everything. |
| Database owner | Everything, including contact details in plain text. Can alter the logs. | Nothing. |

Trust assumptions:

- The verifier is trusted with every private detail and with writing the public text. The checks on a verifier are the event recorded for each decision and a guard that refuses obvious contact details in the public text. Nothing checks a verifier's judgement about what a description might reveal.
- The database owner is outside every control in this document, as in section 2.5.
- The public board is public by design. Its protection is that only reviewed text, a coarse place and a month are shown, and that only published needs ever appear.

Rule for public pages: they show published needs, or counts of them, and nothing else. The map counts are counts of listings that are already public, so they are not differentially private and are not meant to be. Counts of pending, rejected or fulfilled needs are statistics over private data, and belong on the analytics side behind differential privacy once that exists.

Every submission and every verifier decision writes an event (who, when, and the note for a rejection). The event table is append-only for the application, but no page shows it yet, so reviewing a verifier's decisions currently needs database access.
### 2.7 Matching side: threats

Each entry says what the design does, which test in `dev/` shows it, and what is left over.

**Fake or abusive requests.** Sign-up is open, and a verifier reviews every need before it is public.
- Design: nothing reaches the board without approval. A requester can have at most 3 pending needs, each address can create 5 accounts per hour, and the privileged roles cannot be chosen at sign-up.
- Tested: `test_requesters.py` (the fourth pending need and the sixth sign-up from one address are refused; attempts to register as verifier, admin, analyst or field agent are refused and create nothing).
- Left over: many addresses can still flood the queue. The pending limit counts only pending needs, so a requester whose needs were approved can post more. There is no email or phone verification, no CAPTCHA and no password reset. The pending limit uses an advisory lock like the field cap, but only the field cap has a concurrency test.

**Re-identification from the public text.**
- Design: the board shows only the month, category, province, district and the verifier's text. The verifier's form starts from a template, and the server refuses public text containing an `@`, a link, a run of seven or more digits, or the requester's own contact string.
- Tested: `test_verifiers.py` (seven kinds of unsafe text are refused and the need stays pending) and `test_board.py` (no private description, contact detail or review note appears on the board or in the map data, and hostile text is escaped).
- Left over: the guard catches contact details, not descriptions. A name written in words, a street, or a distinctive item in a small district can still point at one household, and anyone can read the board. The contact-string check is a case-insensitive substring match, so a paraphrase passes. This rests on the verifier's judgement.

**A careless or malicious verifier.**
- Design: verifiers are created by script, not by sign-up. Each approval and rejection writes an event. A decision applies only to a pending need, and only verifiers can open the queue or a need's detail.
- Tested: `test_verifiers.py` (all other roles are refused on every verifier route, a second decision on the same need is refused with 409, forged CSRF tokens are refused).
- Left over: a verifier sees every contact detail and writes the public text, and nothing reviews the verifier's decisions. No page shows the event table, so reviewing them needs database access. A rule that a verifier cannot decide a need they posted themselves exists in the update query but is untested, because a verifier cannot post needs. Two verifiers deciding the same need at once is blocked by the same update and the database trigger, but it was only tested one request at a time.

**Scraping the open board.**
- Design: board pages and the map data share a limit of 60 requests per minute per address. Filters and page numbers are validated, and the board sets no cookies.
- Tested: `test_board.py` (requests over the limit get 429, and the limit is shared with the map data).
- Left over: the limit is held in memory, so it resets when the server restarts and is not shared between processes. It uses the connection address, so behind a proxy every visitor looks like one address. Slow scraping stays under the limit. The published data is public by design.

**Contact details at rest.**
- Design: the contact method and detail are stored with each need and shown only to verifiers, never on the board, in the map data, or on the requester's own list. Each method has a format check.
- Tested: `test_contact.py` and `test_board.py`.
- Left over: the details are stored in plain text and readable by the database owner. The checks test the shape, not that a number or address exists or belongs to the requester: any phone number of 7 to 15 digits is accepted. Field-level encryption was not built.

**Sign-up abuse and username probing.**
- Design: usernames and passwords are validated, duplicates are refused with a generic message, and sign-ups are throttled per address.
- Tested: `test_requesters.py` (bad usernames, short passwords, duplicates and forged CSRF tokens are refused).
- Left over: a refused duplicate still confirms that the name exists, so names can be probed within the sign-up limit. Sign-ups are recorded in the same table as failed logins, so five sign-ups from one address count toward that address's login lockout. That interaction was reasoned from the code and not tested.

**Status order and pledges.**
- Design: a database trigger allows only the intended status changes (pending to published or rejected, published to pledged, pledged back to published or on to fulfilled), and an index allows one active pledge per need.
- Tested: `test_needs_db.py` (illegal jumps are refused, a second active pledge is refused, and cancelling frees the need).
- Left over: the trigger checks the order of changes, not who may make them, so role checks live in the web routes (the next entry covers the pledging routes).

**Pledging abuse and supporter contact.**
- Design: a supporter can hold at most 3 active pledges, counted under an advisory lock, and cancelled pledges and fulfilled needs do not count. A need can have only one active pledge (a database index). A supporter's contact is stored with the pledge and shown only to verifiers. Only a verifier can arrange a handover, mark a need fulfilled or release a pledge, each as a conditional update that applies once and writes an event, and a release needs a reason that is stored in the event.
- Tested: `test_supporters.py` and `test_handovers.py` (see section 5). Other roles are refused on every route, no supporter or public page shows a private detail or either contact, five simultaneous pledges by one supporter give exactly three accepted, and two verifiers arranging one pledge at once, or a release racing a supporter's cancel, give exactly one winner.
- Left over: sign-up is open, so one person can create several accounts and hold many pledges, limited only by the sign-up throttle (5 accounts per address per hour). There is no pledge expiry, so an abandoned pledge keeps a need off the board until a verifier releases it, and nothing prompts the verifier. Nothing notifies the supporter or the requester of any change, so everything depends on the verifier contacting both. The verifier sees both contacts and the supporter's username. Release reasons and all pledge events are visible only through the database, because no page shows the event table. Nothing confirms that a handover happened except the verifier's action: neither the requester nor the supporter is asked.

**Boundary data and its licence.**
- Design: the province and district lists come from the OCHA COD-AB Türkiye dataset (CC BY-IGO, via the Humanitarian Data Exchange), credited in the files, the README and under the map. The outline file is not committed.
- Left over: the dataset's methodology says it was shared "for humanitarian use only", and it has not been confirmed that a student prototype is covered. The committed lists of names and codes come from the same dataset, so the same question applies to them. This should be settled with the dataset's contact or the supervisor before the repository is made public or the platform is deployed.
## 3. Evaluation

Run on the 5,000-row seed snapshot (fixed seed 2026), 1,000 trials per cell, through the real `noise.py` functions without touching the budget. Source: `eval_accuracy.py`, output in `eval_accuracy.csv` and `eval_accuracy.png`.

Count query, mean absolute error as a percentage of the true count:

| Region | n | eps 0.05 | eps 0.1 | eps 0.2 | eps 0.5 | eps 1.0 |
|---|---|---|---|---|---|---|
| region_1 | 1197 | 1.7% | 0.8% | 0.4% | 0.2% | 0.1% |
| region_4 | 634 | 3.2% | 1.6% | 0.8% | 0.3% | 0.1% |
| region_7 | 317 | 6.3% | 3.3% | 1.6% | 0.6% | 0.3% |
| region_8 | 193 | 11.0% | 5.3% | 2.6% | 1.1% | 0.5% |

Mean query, median absolute error as a percentage of the true mean (refusal rate was 0.00 everywhere):

| Region | n | eps 0.1 | eps 0.2 | eps 0.5 | eps 1.0 | eps 2.0 |
|---|---|---|---|---|---|---|
| region_1 | 1197 | 4.0% | 1.9% | 0.8% | 0.4% | 0.2% |
| region_4 | 634 | 6.8% | 3.7% | 1.4% | 0.7% | 0.3% |
| region_7 | 317 | 12.6% | 7.1% | 2.9% | 1.4% | 0.7% |
| region_8 | 193 | 23.8% | 11.5% | 4.9% | 2.4% | 1.2% |

Choice: count 0.1, histogram 0.1, mean 0.5, total 10.0. This keeps count error near 5% on the smallest region and brings mean error there to about 5%. A total of 10.0 allows 100 counts or 20 means, or a mix. Keeping the total at 5.0 would allow only about 8 means plus a few counts, which was judged too small for several analysts. This is a utility-versus-privacy decision and sits at the top of the commonly used range of 1 to 10.

Notes: the mean table reports the median, and the ratio of two noisy values has heavy tails, so a typical bad draw is worse. Tables here were measured for the old fixed per-region queries. In the engine a full table of eight regional counts costs 0.1, not 0.8, because the cells are disjoint. Mean cells over many small groups (for example region by household size) are mostly suppressed.

## 4. Out of scope and known limits

- Real data. Only synthetic data was used.
- Person-level guarantee. The server generates a new pseudonym per submission, so nothing prevents the same real person being entered twice. The guarantee is per record, and per person only if intake deduplicates outside this system. The same person across several datasets is also not covered.
- Auxiliary information. Attackers who know other facts about individuals are not modelled beyond what differential privacy provides.
- Adjacency. The guarantee is for add/remove of one person. If a person's record is edited so they move between cells, two cells change, and the effective epsilon for that event is about double. Engine means are tested only through their sum and count components, not as a ratio.
- Stored results. The results table holds noisy outputs, readable by the admin and by the database owner. They are post-processing of charged answers, so they cost no extra epsilon, but they show what analysts received. Suppression at 30 is a usability flag, not protection. Engine means are tested only through their sum and count components.
- Floating-point Laplace sampling. General-purpose libraries have known precision-based leaks (Mironov 2012). diffprivlib documents this and it is accepted here.
- A growing dataset. Records added after a query change what earlier queries saw. The budget is per dataset snapshot, not per lifetime of a growing dataset, and the evaluation used the seed snapshot.
- Transport and deployment. No TLS and no `Secure` cookie flag (local http only). Behind a reverse proxy every client would share one IP for the login limit.
- Session theft. A stolen valid cookie works until it expires. There is no server-side revocation list.
- Denial of service. Anyone can lock a username for 5 minutes by failing logins, and one analyst can exhaust the budget.
- Slow guessing. An attacker staying under 5 attempts per 5 minutes per username is not blocked. argon2 makes each guess costly.
- Side channels. Timing is only partly equalised (login). A refusal or a budget-exhausted message depends on state.
- Database owner, host compromise, backups, and key management.
- Unimplemented items from the plan: field-level encryption, hash-chained audit logs, per-user budget caps, admin account management, UI styling. Matching side: notifications, pledge expiry, confirmation of a handover by the requester or the supporter, analytics over the needs data, email or phone verification, editing or withdrawing a need, a page showing the event table, and a way for someone to ask for their data to be removed.
- Sign-in has a minimum password length only at seed time (12 characters); there is no password change page.

Argued but not tested:
- Formal epsilon-differential privacy. There is no proof and no formal audit. The sum sensitivity of 500 follows from the SQL clipping and is argued, not measured. The histogram's privacy follows from the count mechanism being applied per disjoint bin.
- A stolen database yields only hashes and pseudonymous plain-text records. Not attempted.
- The audit log is append-only against the app role. Tested for `dp_app`; the owner is outside this claim.

Reasoned from the code, not tested (matching side):
- A verifier cannot decide a need they posted: the update query excludes it, but a verifier cannot post needs, so the case never occurs.

- The pending-needs limit under simultaneous posts: guarded by an advisory lock, with no concurrency test.
- Sign-ups counting toward the login lockout of the same address.
- The board's rate limit across several server processes, or behind a proxy.
- Two supporters pledging one need in the narrow window where both pass the availability check: blocked by the conditional update and the one-active-pledge index, but the test only produced the loser arriving after the winner had committed.
- That a handover really happened: the verifier's action is the only record.

## 6. Reproducing

`requirements.txt` pins the environment. `schema.sql` builds every table, including the needs tables, the results table and the login-failure log. `seed.py` creates 5,000 synthetic beneficiaries, `seed_users.py` creates the analyst, admin and field-agent accounts, and `seed_verifier.py` creates a verifier. Settings and secrets live in `.env`; copy `.env.example` to `.env` and fill in the placeholders. The province and district lists are committed; the map outlines are not, and `README.md` explains how to rebuild them. Most tests in `dev/` need the database owner's password and create throwaway accounts. The last run from a fresh clone (commit `fa16031`) covered only the analytics path. The matching side, verifier seeding and the boundary-file rebuild have not been run from a clean clone.
